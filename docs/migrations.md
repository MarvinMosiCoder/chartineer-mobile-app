# PostgreSQL migrations

The backend uses `node-pg-migrate` 9.x. SQL migration files live in `backend/migrations/`. Run commands in this guide inside `backend/`.

## Connection setup

The migration script in `backend/package.json` is:

```json
"migrate": "node --env-file=.env ./node_modules/node-pg-migrate/bin/node-pg-migrate.js"
```

Node loads `.env` before the CLI starts. The installed CLI supports `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, and `PGPASSWORD`, as used by the API. Follow the [setup guide](setup.md#first-time-setup) for a new database and application account.

## Existing users migration

The first file is [1791517085689_create-users.sql](../backend/migrations/1791517085689_create-users.sql):

```sql
-- Up Migration

CREATE TABLE public.users (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email TEXT NOT NULL,
  password_hash TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE UNIQUE INDEX users_email_unique
ON public.users (LOWER(email));

-- Down Migration

DROP TABLE public.users;
```

| Column | Meaning |
| --- | --- |
| `id` | Automatically generated user ID |
| `email` | Login email, unique ignoring capitalization |
| `password_hash` | Password hash to be generated by the backend |
| `created_at` | Creation timestamp with time zone |

This migration creates the schema; it does not insert accounts. Authentication and hashing are upcoming work.

## Apply pending migrations

```powershell
npm run migrate -- up
```

The CLI applies pending Up sections and records them in `public.pgmigrations`. After success, another `up` should have no pending changes. Use this command to bring a new database up to the existing schema. See the [version 9 CLI reference](https://github.com/salsita/node-pg-migrate/blob/v9.0.0/docs/src/cli.md).

## Inspect the result

Open pgAdmin Query Tool on `chartineer`:

```sql
SELECT id, email, created_at FROM public.users;

SELECT name, run_on
FROM public.pgmigrations
ORDER BY run_on;
```

An empty users result is expected before account creation. History should contain the migration's name and execution time.

## Create a future migration

For example, to add an optional display name:

```powershell
npm run migrate -- create add-user-display-name --migration-file-language sql
```

Edit the new timestamp-prefixed file:

```sql
-- Up Migration

ALTER TABLE public.users ADD COLUMN display_name TEXT;

-- Down Migration

ALTER TABLE public.users DROP COLUMN display_name;
```

This is a future-feature example; the current table does not contain `display_name`. Save the migration and apply it with `npm run migrate -- up` when intentionally adding that feature. Keep the Up and Down comment markers, which split the file into its two operations.

Once a migration has been applied, put subsequent changes in a new migration so databases with existing history receive them too. Keep generated filenames intact because their prefixes determine ordering. When using Git, commit migration files with the feature that needs them.

## Roll back one migration

```powershell
npm run migrate -- down
```

This runs the latest applied migration's Down section. For `create-users`, it drops the users table and its accounts. For the display-name example, it removes the column and its values. Inspect the Down SQL and use rollback only when you intend those effects; back up data before reversing changes that contain it.

Run `npm run migrate -- up` to apply the reverted migration again. Recreating the schema does not restore deleted data.

## Migration errors

| Error | What to check |
| --- | --- |
| `.env` not found | Run in `backend/` and create `.env` |
| Password authentication failed | Match the username and password to the database role |
| Database does not exist | Match `PGDATABASE` to the database you created |
| Permission denied for schema public | Confirm the account owns the database or has the required schema permissions |
| Relation users already exists | Inspect `users` and `pgmigrations` before retrying the first migration |

Do not mark a migration applied just to bypass an error. Resolve the schema or connection mismatch, then rerun `up`.
